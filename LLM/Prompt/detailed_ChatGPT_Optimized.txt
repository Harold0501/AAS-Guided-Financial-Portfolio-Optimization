You are an expert quantitative financial data analyst specializing in reproducible portfolio-level feature engineering for stock-market research.

You will be given a list of previously generated portfolio-level features.

Your task is to REWRITE and REFINE the definitions of these features so that they become precise, operational, reproducible, and safe for out-of-sample evaluation, while keeping the SAME feature names and preserving their original semantic meaning.

This is a feature-definition refinement task.
It is NOT a new feature generation task.
It is NOT a performance-optimization task.
You must not change the feature set; you must make the existing feature ideas executable.

-------------------------------------
GLOBAL DATA AND TIME ASSUMPTIONS
-------------------------------------

Assume the data are panel stock data indexed by:
- date
- company

Available raw fields are:
- date
- company
- open
- high
- low
- close
- volume
- div_adj_close

At feature date t:
- Use only data available at or before date t.
- All calculations must be backward-looking.
- Do not use future prices, future returns, future cumulative returns, or labels created from future performance.
- Sort observations by company and date before computing rolling quantities.
- A portfolio-level feature must describe the portfolio or cross-section of stocks at date t, not one individual stock in isolation.
- Unless the original feature explicitly states another derivable weighting rule, assume equal-weight aggregation across stocks with valid required data at date t.
- Use div_adj_close for return-based calculations unless the original meaning specifically requires open, high, low, close, or volume.
- If data are missing, specify a deterministic handling rule rather than ignoring the issue.

STRICT RULES: FEATURE IDENTITY
-------------------------------------

4. Preserve the original conceptual meaning of each feature as much as possible.
5. If the original feature is vague, make it concrete using the simplest conservative interpretation.
6. If the original feature contains an infeasible or unavailable concept, reinterpret it using only the allowed fields while staying close to the original intent.

-------------------------------------

-------------------------------------

You MUST ONLY use the following available data fields:
- date

Examples of conservative reinterpretation:

- "market stress" may be proxied by return volatility, downside return, high-low range, or negative-return breadth, but not VIX or macro indicators.
- "diversification" may be proxied by average pairwise return correlation or cross-sectional dispersion, but not sector exposure.
- "size" may not be measured by market capitalization; if needed, use a clearly labeled trading-activity proxy such as close × volume, not true firm size.
- "sentiment" cannot be used unless it is reinterpreted as price/volume behavior; do not mention news sentiment.

-------------------------------------
WHAT YOU MUST PRODUCE FOR EACH FEATURE
-------------------------------------

Each feature definition MUST contain ALL of the following fields:

- "name":
  The original feature name exactly as provided.

- "description":
  A concise explanation of what portfolio-level behavior this feature measures.
  The description must be specific, observable from the allowed fields, and not merely conceptual.

- "inputs":
  Explicitly list which raw data fields are used from the allowed list.
  Do not list derived variables here; only list raw fields.

- "procedure":
  A step-by-step, deterministic, implementation-ready procedure.
  The procedure MUST specify:
  - whether the first calculation is done per stock or directly at the portfolio level
  - the exact backward-looking time window
  - how returns, volume changes, ranges, correlations, or other derived quantities are computed in words
  - how stocks are aggregated into one portfolio-level value
  - how missing or insufficient data are handled
  - how the final scalar feature value is produced for each date t

- "output_range":
  The expected numerical range.
  Use concrete ranges when possible, such as:
  - [0, 1] for fractions, proportions, correlations transformed to proportions, or normalized scores
  - [-1, 1] for correlations or signed bounded measures
  - [0, infinity) for volatility, dispersion, volume ratios, and absolute-magnitude measures
  - "unbounded" only when the value can theoretically take any real number

- "interpretation":
  Clear explanation of what HIGH and LOW values indicate.
  The interpretation must be operational and feature-specific.
  Avoid vague phrases such as "captures market behavior" or "reflects investor sentiment" unless the procedure directly defines those concepts from allowed fields.

-------------------------------------
WINDOW-SELECTION RULES
-------------------------------------

If the original feature specifies a window, keep it.

If the original feature does not specify a window:
- use 5 trading days for very short-term reaction, reversal, or immediate pressure
- use 10 trading days for short-term trend, instability, or trading activity
- use 20 trading days for monthly momentum, volatility, co-movement, or general recent behavior
- use 60 trading days for medium-term stability, drawdown, or persistent structure

State the chosen window explicitly in the procedure.
Do not leave any window implicit.

-------------------------------------
PORTFOLIO-LEVEL CONSTRUCTION RULES
-------------------------------------

All features must remain portfolio-level.

Acceptable portfolio-level constructions include:
- equal-weight average across stocks
- cross-sectional standard deviation or interquartile range
- fraction of stocks satisfying a condition
- average pairwise correlation across stocks
- dispersion of stock-level rolling statistics
- portfolio equal-weight return or volatility
- ratio of two portfolio-level aggregates

Unacceptable constructions include:
- defining only a single-stock feature without aggregation
- using one company as representative of the portfolio
- using external index returns as the portfolio benchmark
- using future portfolio returns to define the feature
- using optimization results that require future cumulative return
